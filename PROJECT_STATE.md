# Platum — Current Implementation State

This Stage 4 technical snapshot describes inspected implementation and scoped verification. The dated release checkpoint distinguishes confirmed hosted facts from unresolved access. AGENTS.md contains working rules and context pointers.

## 1. Current product

Platum, previously Cabinet and Client Cabinet, is an independent client-service workspace. The authenticated interface supports the shared client/team cycle plus Stage 2 scheduling, learning/practice, inspiration, milestones, period reports and reusable templates. The initial audience is clients managed by the MOTN team; the implementation remains agency-neutral.

## 2. Major capabilities

- **Access and team management:** Confirmed users enter through Supabase Auth. A server API creates workspaces, sends or resends invitations, and revokes invitations or memberships. The global founder-role migration was applied to Supabase on 2026-10-17; its matching source was published with the community release on 2026-10-20 (sections 10 and 12). Other participants remain scoped to explicit workspace memberships. Membership changes go through server commands and invitation acceptance; direct authenticated membership writes are denied. The current source disables the public demo preview.
- **Agreement and personalisation:** The team edits goals, scope, roles, working rhythm, boundaries, current focus, next step, welcome text, accent, and section order/visibility through the interface. Navigation visibility does not replace authorization. Existing strategy and milestone records remain readable.
- **Requests and tasks:** Clients describe a need and can attach a file. Operators classify scope, assign a team owner, reply, and create linked tasks. Clients complete their eligible tasks. Writes use revision checks and operation IDs; stale edits report conflicts and repeated requests do not duplicate accepted changes.
- **Materials and review:** Structured text sections, reference links, and attachments form immutable material versions. Drafting and publishing are separate. Discussions bind to a version and optional stable section; client approval/change requests and reading state are separate records. A new publication does not inherit an older approval. Team drafts remain inaccessible to clients.
- **Questionnaires:** Operators configure supported question types and explanations. Clients save private answer drafts, submit responses, and reuse matching earlier answers when questions change. Submitted responses retain their original question definitions. The team reviews submitted responses; older unversioned records remain preserved.
- **Files and exports:** A private Supabase bucket supports documents/images up to 10 MB with reserved immutable paths. Downloads pass through the server, which checks current file visibility under the user's RLS before streaming bytes with no-store headers; direct client Storage reads are denied. Team files stay internal until explicitly shared or attached to a shared request/published material. Large videos remain external links. Markdown and JSON exports use a server-enforced shared-data projection; file bytes are downloaded separately.
- **Updates and team inbox:** Real requests, tasks, submissions, material decisions, published updates, and recorded decisions drive the interface. The team sees pending requests, responses, and requested changes across assigned workspaces. Per-user read markers identify new content. Section navigation refreshes data; pending saves and editor drafts are protected from automatic focus refreshes.

- **Calendar and availability:** Either side proposes or reschedules an event, the other side confirms, and immutable proposals retain their decisions/discussion. Members share time zones, weekly availability and unavailable dates. The month view includes task/milestone dates; ICS exports preserve the current event state. External calendar synchronization is not configured.
- **Learning and inspiration:** Published material versions support short lessons, files and discussion. Clients save private practice drafts, submit attempts and receive explicit team feedback. Revised lessons do not inherit completion. Shared inspiration has tags, project links and discussion snapshots; team drafts stay internal.
- **Progress and reports:** Milestones connect shared tasks and result versions, require completion evidence and retain their history. Period reports publish immutable snapshots with verified metric sources, selected results and dated completed work. Discussion and approval remain version bound.
- **Reusable templates:** Operators author configuration and material, form or learning definitions. Applying a template checks source and destination access, creates internal drafts, and changes configuration only when selected. Memberships, client answers, files and history are not copied.

- **Contacts and communities:** The first contact/community implementation is published (section 12). Workspace contacts remain operator-only. Independent invited communities retain opt-in profiles, discussion, versioned events/attendance, reviewed participant referrals and explicit invitation/revocation; community membership never grants client-workspace access. The next source change restricts community publication to managers and adds revision-bound voluntary participation/self-reports with manager summaries; this change requires the new migration and is not published (section 13). No real accounts, memberships, posts or invitations are created by either migration.

## 3. Technical foundation

Static HTML, CSS, and vanilla JavaScript remain the frontend stack. The collaboration surface reuses existing Auth and database foundations; the earlier portal/Agency OS remains an isolated preview.

Supabase Auth, PostgREST, transactional RPCs, RLS, and private Storage provide persistence. New privileged functions live in the private schema behind explicitly granted public wrappers. The Node API uses server-only credentials for Auth invitations and scoped administration. Browser code contains only the publishable key and user session. The collaboration migration must precede the new frontend, and server configuration must target the same Platum backend.

Production target: https://client-cabinet.vercel.app. The alternate https://platum-client-agency-workspace.vercel.app redirects there so browser origins and Auth callbacks agree. The canonical address remains a deployment alias and must be verified/reassigned during publication. The Stage 1 and Stage 2 migrations and server URL/secret/app origin are configured. The first operator accepted a real email invitation and created a workspace through the published interface; the one-time bootstrap allowance was then removed from production configuration. Global roles and the first contacts/community schema/source were released by 2026-10-20 (section 12). The new community-participation source requires the separate additive migration `20261021120000_community_participation.sql`, which this task has not applied to production.
